# 金融租赁实时数仓建模实践文档

> 技术栈：Flink CDC → Kafka → Doris（DataStream API）
> 状态：五层全部完成（ODS + DIM + DWD + DWS + ADS），FineBI 可视化完成

---

## 一、项目概述

### 1.1 整体架构

```
MySQL(金融租赁业务库 financial_lease)
   │  Flink CDC 采集 binlog（DataStream API）
   ▼
Kafka（ODS 层，动态路由：每表一个 topic，命名 ods_表名）
   │  Flink 读取 Kafka（DataStream API）
   ▼
Doris（数仓建模：DIM / DWD / DWS / ADS 四层）
```

### 1.4 业务库 financial_lease（9 张表）

**维度表（4 张）**：department（部门）、employee（员工）、industry（行业）、business_partner（商业合伙人/申请人）

**事实表（5 张）**：
- credit_facility（授信申请，核心主表）
- credit_facility_status（审核记录/流水）
- reply（批复）
- credit（授信）
- contract（合同）

**业务链路**：申请人 → 授信申请 → 多级审批（可复议）→ 批复 → 授信 → 合同签约起租

## 二、第一阶段：Flink CDC → Kafka（ODS 层）

### 2.1 目标

用 Flink CDC 采集 MySQL 的 binlog，以 Debezium JSON 格式写入 Kafka，作为数仓 ODS 层。采用「单作业整库读取 + Sink 动态路由」：一个 CDC 作业读 financial_lease 全部 9 张表，按每条数据的 `source.table` 字段自动路由到专属 topic（命名 `ods_表名`）。

### 2.2 关键选型

| 决策点 | 选择 | 原因 |
|--------|------|------|
| Flink CDC 版本 | **2.4.2** | 2.3.0 不兼容 Flink 1.17，会报 NoClassDefFoundError |
| 实现方式 | DataStream API | 用户要求，且后续数仓建模也用 DataStream |
| 数据格式 | Debezium JSON（JsonDebeziumDeserializationSchema） | 保留 before/after/op 完整变更语义，供下游 debezium-json 解析 |
| Topic 路由 | 单作业 + TopicSelector 动态路由 | 每表一个 topic，下游各表独立作业，架构清晰 |

```java
    JsonNode source = node.get("source");
    return source.get("table").asText();
}

KafkaSink<String> kafkaSink = KafkaSink.<String>builder()

                        .setTopicSelector(record -> "ods_" + extractTableName(record))
                        .setValueSerializationSchema(new SimpleStringSchema())
                        .build()
        )
        .setDeliveryGuarantee(DeliveryGuarantee.AT_LEAST_ONCE)
        .build();

cdcStream.sinkTo(kafkaSink);
```

## 三、第二阶段：Kafka → Doris（DIM 层）

### 3.1 目标与设计

用 Flink DataStream 读 Kafka 的 `ods_` 原始数据，做**原始镜像（raw mirror）**写入 Doris 的 `dim` 库——不拍平、不加工，类型对齐 MySQL 源表，保留层级字段（`department_level` / `superior_department_id` / `industry_level` / `superior_industry_id`），供 DWD / DWS 关联时按需解析。

**维度表（4 张，与业务库维度表 1:1 映射）：**

| 维度表 | 对应 ODS Topic | 主键 | 说明 |
|--------|----------------|------|------|
| dim_business_partner | ods_business_partner | id | 商业合伙人/申请人 |
| dim_department | ods_department | id | 部门，保留 level + superior_department_id |
| dim_employee | ods_employee | id | 员工，保留 department_id |
| dim_industry | ods_industry | id | 行业，保留 level + superior_industry_id |

> 为什么用「原始镜像」而不是「拍平」？行业/部门的 3 级树拍平统一放到 DWS 层用广播状态做（见第六节），维度表保持原始结构、一份数据多处复用，避免在 DIM 层重复加工。

**类型映射**：id → BIGINT，name → VARCHAR，level / type / superior_*_id → BIGINT（编码不翻译）

### 3.2 Doris 建表（Unique Key 模型）

以 `dim_business_partner` 为例（完整见 `sql/dim_ddl.sql`）：

```sql
CREATE DATABASE IF NOT EXISTS dim;

CREATE TABLE IF NOT EXISTS dim.dim_business_partner (
    id          BIGINT       COMMENT '合伙人/客户主键ID',
    create_time DATETIMEV2   COMMENT '记录创建时间',
    update_time DATETIMEV2   COMMENT '记录更新时间',
    name        VARCHAR(256) COMMENT '合伙人/客户名称'
)
UNIQUE KEY (id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ('replication_num' = '2');
```

### 3.3 关键代码

四个作业结构完全一致：`Kafka(ods_xxx) → map 解析 → filter 过滤 delete → toJson → DorisSink`。以 `DimDepartmentJob` 为例：

```java
public class DimDepartmentJob {
    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        env.setParallelism(1);
        // 关键：Doris sink 依赖 checkpoint 才 flush，必须开启
        env.enableCheckpointing(10000);
        env.getCheckpointConfig().setCheckpointStorage("file:///opt/module/flink-1.17.1/checkpoints");

        DataStream<String> jsonStream = env.fromSource(
                DimUtil.buildKafkaSource("ods_department", "dim_department_group"),
                WatermarkStrategy.noWatermarks(),
                "ods_department");

        DataStream<DimDepartment> deptStream = jsonStream
                .map(DimDepartmentJob::parse)   // 取 Debezium JSON 的 after，delete 操作返回 null
                .filter(d -> d != null);

        deptStream.map(DimUtil::toJson)
                .sinkTo(DimUtil.buildDorisSink("dim.dim_department", "label-dep"));

        env.execute("DIM Department");
    }

    private static DimDepartment parse(String json) {
        JsonNode after = DimUtil.getAfter(json);
        if (after == null) {
            return null;
        }
        DimDepartment d = new DimDepartment();
        d.id = after.get("id").asLong();
        d.departmentLevel = DimUtil.getNullableInt(after, "department_level");
        d.departmentName = after.get("department_name").asText();
        d.superiorDepartmentId = DimUtil.getNullableLong(after, "superior_department_id");
        return d;
    }
}
```

**DimUtil 关键点**（四个作业共用）：

```java
// 从 Debezium JSON 中取 after（delete 操作 after 为 null，由 filter 过滤）
public static JsonNode getAfter(String debeziumJson) { ... }

// Doris Sink：JSON 格式 stream load，直连 BE，关闭 delete 支持
DorisOptions options = DorisOptions.builder()
        .setFenodes("hadoop100:8030")
        .setBenodes("hadoop101:18040,hadoop102:18040")   // 直连 BE，绕开 FE 重定向
        .setTableIdentifier(tableIdentifier)
        .setUsername("root")
        .setPassword("root")
        .build();

DorisExecutionOptions executionOptions = DorisExecutionOptions.builder()
        .setLabelPrefix(labelPrefix + "_" + System.currentTimeMillis())   // label 唯一，避免重启撞 Label Already Exists
        .setDeletable(false)   // 关闭 delete 支持，避免 __DORIS_DELETE_SIGN__ 报错
        .setStreamLoadProp(props)   // format=json, read_json_by_line=true
        .build();

DorisSink.<String>builder()
        .setDorisOptions(options)
        .setDorisExecutionOptions(executionOptions)
        .setSerializer(new SimpleStringSerializer())
        .build();
```

## 五、第三阶段：Kafka → Doris（DWD 明细层）

### 5.1 目标与设计

用 Flink DataStream 读 Kafka 的 5 张事实源表（credit_facility、credit_facility_status、reply、credit、contract），按业务事件拆分成 **8 张事务事实表**，写入 Doris 的 `dwd` 库。采用**单作业动态分流**架构：一个 `DwdBaseJob` 读 5 表 union 成一条流，按 `credit_facility_id` 分组，进 `KeyedProcessFunction` 做「谁先到谁等」状态合并，通过侧输出流分流到 8 张事实表。

**8 张事实表分三个数据域：**

| 数据域 | 事实表 | 说明 |
|--------|--------|------|
| 审批域 | dwd_audit_approve / reject / cancel | 审批通过 / 拒绝 / 取消 |
| 授信域 | dwd_credit_add / occupy | 新增授信 / 授信占用 |
| 租赁域 | dwd_lease_contract_produce / sign / execution | 合同制作 / 签约 / 起租 |

> 批复（reply）不单独建表，合并进「审批通过」事实表。

### 5.2 事实表与事件检测规则（核心）

事件检测是整个 DWD 层的灵魂，规则如下（都是从业务状态机 + 建表注释推导出来的）：

| 事实表 | 事件检测规则 | 主键 + 分区字段 |
|--------|-------------|----------------|
| dwd_audit_approve | `credit_facility_status.status=16`（出具批复审核通过） | id + approve_time |
| dwd_audit_reject | `credit_facility_status.status=20`（拒绝，终态） | id + reject_time |
| dwd_audit_cancel | `credit_facility_status.status=21`（取消，终态） | id + cancel_time |
| dwd_credit_add | credit 表插入（`op=r` 快照 / `op=c` 增量） | id + add_time |
| dwd_credit_occupy | `credit.credit_occupy_time` 非空 | id + occupy_time |
| dwd_lease_contract_produce | `credit.contract_produce_time` 非空 | id + produced_time |
| dwd_lease_sign | `contract.signed_time` 非空 | id + signed_time |
| dwd_lease_execution | `contract.execution_time` 非空 | id + execution_time |

**关键字段来源（三张金额字段）：**

| 字段 | 来源 |
|------|------|
| apply_amount（申请金额） | `credit_facility.credit_amount` |
| reply_amount（批复金额） | `reply.credit_amount` |
| credit_amount（授信金额） | `credit.credit_amount` |
| audit_man_id（信审经办） | `credit_facility_status.status∈(4,5,6)` 的 employee_id |

**状态机关键结论（从建表注释读出的）**：
- `credit_facility.status`：16=出具批复审核通过（审批通过）、**19=新增授信**、20=拒绝、21=取消。16 不是终态，会流转到 19，所以「审批通过」必须用 `credit_facility_status` 流转记录检测，不能看 `credit_facility.status` 当前值。
- `credit.status`：1=新建、2=已占用、3=已制作合同、4=已取消。占用/制作要按时间字段（credit_occupy_time / contract_produce_time）判断，不能按 status。
- `contract.status`：1=新建、2=已签约、3=已起租。签约/起租按 signed_time / execution_time 判断。

### 5.3 关键设计决策（5 个）

1. **单作业 + 侧输出流动态分流**：借鉴尚硅谷 DwdBaseApp，但下游直接落 Doris（不是 Kafka），状态生命周期必须可靠。

2. **主输出 + 全部侧输出统一为 String(JSON)**：Flink 对「异构 POJO 侧输出」有类型传播 bug（见踩坑 #1），统一成 String 后永不报 cast 错。业务状态仍在函数内部用 POJO `ValueState` 维护，只在 `collect` 时转 JSON。

3. **谁先到谁等（Keyed ValueState + 1 小时 TTL）**：多表按 `credit_facility_id` 分组，先到的存状态、后到的补全后发射。TTL 不能太短（快照多表到达时间差大，30 秒会误清），也不能无 TTL（异常分支状态永久残留）。

4. **审批通过 4 路关联**：status=16 事件 + facility 字段 + 信审经办（4/5/6）+ 批复（reply），四者到齐才发射。

5. **credit/contract 事件按时间字段判断，且独立触发**：一条 credit 记录可能同时触发 add + occupy + produce（经历过三个阶段），所以是三个独立 if，不是 if-else。

### 5.4 Doris 建表（DUPLICATE KEY + 动态分区）

8 张表结构相同，以 dwd_audit_approve 为例（完整见 `sql/dwd_ddl.sql`）：

```sql
CREATE DATABASE IF NOT EXISTS dwd;

CREATE TABLE IF NOT EXISTS dwd.dwd_audit_approve (
    id                   BIGINT          COMMENT '授信申请ID',
    approve_time         DATETIMEV2      COMMENT '审批通过时间',
    lease_organization   VARCHAR(255)    COMMENT '业务方向',
    business_partner_id  BIGINT          COMMENT '申请人ID',
    industry_id          BIGINT          COMMENT '行业ID',
    reply_id             BIGINT          COMMENT '批复ID',
    salesman_id          BIGINT          COMMENT '业务经办ID',
    audit_man_id         BIGINT          COMMENT '信审经办ID',
    apply_amount         DECIMAL(19,2)   COMMENT '申请授信金额',
    reply_amount         DECIMAL(19,2)   COMMENT '批复授信金额',
    reply_time           DATETIMEV2      COMMENT '批复时间',
    irr                  DECIMAL(19,2)   COMMENT '还款利率',
    period               INT             COMMENT '还款期数'
)
DUPLICATE KEY(id, approve_time)
COMMENT 'DWD层-审批域-授信审批通过事务事实表'
PARTITION BY RANGE(approve_time) ()
DISTRIBUTED BY HASH(id) BUCKETS 10
PROPERTIES (
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
```

| # | 坑 | 现象 | 根因 | 解决 |
|---|-----|------|------|------|
| 1 | **异构 POJO 侧输出 ClassCastException** | `DwdAuditReject cannot be cast to DwdAuditApprove`，作业反复 RESTARTING | Flink 对异构 POJO 侧输出有类型传播 bug，所有 side output 被当成主输出类型 | 主输出+侧输出统一成 String(JSON)，业务状态仍用 POJO ValueState 内部维护 |

| 4 | credit_occupy 空（0 行） | 授信占用表无数据 | 用 `credit.status==2` 判断，但「当前占用」只有 2 条 | 改 `credit_occupy_time 非空` |
| 5 | credit_add/contract_produce 偏少 | 123 / 91，远低于源表 | credit 事件错误绑定在「审批通过」上，被 approval 卡住 | credit 事件由 credit 表生命周期独立触发（插入/占用时间/制作时间） |
| 6 | reject/cancel 漏数 | 1088→866、269→168 | 谁先到谁等 audit_man_id，导致无信审经办的拒绝/取消被永久丢弃 | 改从 credit_facility_status 检测 + audit_man_id 可空 |
| 7 | lease_sign 偏少 | 884，漏掉已起租合同 | 用 `contract.status==2` 只算当前已签约 | 改 `signed_time 非空`（含已起租的合同） |
| 8 | decimal 是 base64 | 金额乱码 | Debezium 把 decimal 序列化成 base64（unscaled BigInteger） | decodeDecimal(base64, scale) 解码 |
| 9 | Label Already Exists | 作业重启后报 label 已存在 | Doris label 前缀重复 | labelPrefix 加时间戳后缀 |

## 六、第四阶段：Kafka → Doris（DWS 汇总层）

### 6.1 目标与设计

用 Flink DataStream 读 DWD 双写的 Kafka topic（`dwd_*`），做 **10 秒滚动窗口聚合**，写入 Doris 的 `dws` 库，构建汇总层。DWD 作业除写 Doris 外，同时双写一份 JSON 到 Kafka（`dwd_audit_approve`、`dwd_credit_add` 等），供 DWS 实时消费。

**11 张 DWS 表分三类：**

| 类别 | 表 | 分组粒度 |
|------|-----|---------|
| 无维度（5 张） | dws_credit_credit_add/occupy_win、dws_lease_contract_produce/sign/execution_win | 纯时间窗口（`windowAll`，不分组） |
| 行业+业务方向+经办人（3 张） | dws_audit_industry_lease_organization_salesman_approval/cancel/reject_win | 业务方向 + 行业3级 + 业务经办 |
| 信审经办（3 张） | dws_audit_audit_man_approval/cancel/reject_win | 信审经办 |

表模型：AGGREGATE KEY（stt/edt/cur_date + 维度字段）+ 指标 REPLACE（Flink 窗口内聚好后，Doris 幂等覆盖）。

### 6.2 关键设计决策

1. **DWD 双写 Kafka**：DWD 作业每个输出同时 `sinkTo(Doris)` + `sinkTo(Kafka)`（`DimUtil.buildKafkaSink`），提供流式数据给 DWS。
2. **事件时间水位线 + 10 秒滚动窗口**：读 `dwd_*` topic，按各事件时间字段（add_time/occupy_time/signed_time/approve_time 等）提事件时间，`keyBy`（或无维度用 `windowAll`）→ 10 秒窗口 → `reduce` 累加 count + 金额 → `ProcessWindowFunction` 补 stt/edt/cur_date。
3. **维度广播拍平**（替代参考的 HBase 异步 I/O）：用 `DwsDimUtil` 从 ODS Kafka 广播 3 张维度表（`ods_industry`/`ods_employee`/`ods_department`），主流窗口聚合后 `connect(broadcastStream).process(BroadcastProcessFunction)`，在 `processElement` 里向上查 `superior_industry_id` / `superior_department_id` 做 3 级拍平 + 员工/信审经办姓名。
4. **维度数据源一致性**：Doris dim 表是 DIM 作业从 ODS 原始数据 raw mirror 的，所以广播 ODS 原始 topic 和 dim 表是同一份数据，拍平结果一致（已验证）。

### 6.3 关键代码（维度广播，`DwsDimUtil`）

```java
// 从 ODS 读 3 张维度表，统一成 DimRow（table + id + data），union 后广播
public static DataStream<DimRow> buildDimBroadcastStream(StreamExecutionEnvironment env) {
    DataStream<DimRow> industry   = readDim(env, "ods_industry",   "dws_dim_industry_group");
    DataStream<DimRow> employee   = readDim(env, "ods_employee",   "dws_dim_employee_group");
    DataStream<DimRow> department = readDim(env, "ods_department", "dws_dim_department_group");
    return industry.union(employee, department);
}
// 广播状态：key = "表名:id"，value = 维度整行 Map（用 TypeHint 显式指定类型，避免菱形推断失败）
public static final MapStateDescriptor<String, Map<String, Object>> DIM_DESC =
        new MapStateDescriptor<>("dim_state",
                TypeInformation.of(String.class),
                new TypeHint<Map<String, Object>>() {}.getTypeInfo());

// 主流窗口聚合后：BroadcastStream 必须用它 connect，才能用 BroadcastProcessFunction
BroadcastStream<DimRow> dimStream = DwsDimUtil.buildDimBroadcastStream(env).broadcast(DwsDimUtil.DIM_DESC);
dimmed = reduced.connect(dimStream)
        .process(new BroadcastProcessFunction<Bean, DimRow, Bean>() {
            processBroadcastElement: dimState.put(row.table + ":" + row.id, row.data);  // 填充维度
            processElement: 查 dimState 拍平（行业/部门向上查 3 级 + 员工姓名）后 collect
        });
```

### 6.5 踩坑记录（DWS 层，都是新坑）

| # | 坑 | 现象 | 解决 |
|---|-----|------|------|
| 1 | 时间字段 `@JsonProperty` 用反 | 窗口不触发（事件时间=0，DWS 表空） | 供水位线的时间字段（add_time/occupy_time/approve_time 等）用 **WRITE_ONLY**（只反序列化读入、不序列化输出）；READ_ONLY 是反的 |
| 2 | Bean 缺 `@JsonIgnoreProperties` | `UnrecognizedPropertyException`（DWD JSON 有多余字段） | Bean 类加 `@JsonIgnoreProperties(ignoreUnknown = true)` |
| 3 | 时间字段名不匹配 | occupy/produce 表空（`occupy_time` vs `credit_occupy_time`） | `@JsonProperty` 值要和 DWD POJO 输出字段名完全一致（以 DWD JSON 实际为准） |
| 4 | `MapStateDescriptor` 菱形推断失败 | 编译报错 | 用 `TypeInformation.of` + `new TypeHint<Map<String,Object>>(){}` 显式指定 |
| 5 | `BroadcastStream` 类型不对 | `process(BroadcastProcessFunction)` 找不到方法 | 声明为 `BroadcastStream`（`.broadcast()` 返回的是它），用它 `connect` 才能用 BroadcastProcessFunction |
| 6 | 维度广播时序/offset | 个别记录维度名 NULL | 重置广播 consumer group（`dws_dim_industry/employee/department_group`）从 earliest 重读 |
| 7 | 维度名变化导致 AGGREGATE KEY 重复 | 重跑后 name NULL 和有值两行并存 | 清表 + 重置广播 group 后重跑（name 全有值，key 一致 REPLACE 覆盖） |

| 方式 | 实时性 | 复杂度 | 结论 |

### 7.3 核心 SQL（物化视图示例）

## 八、通用经验总结

1. **Flink CDC 版本要和 Flink 版本严格匹配**：Flink 1.17 对应 CDC 2.4.x，不是 2.3.x。
2. **排错先看报错的具体字段**：checkNotNull 空指针，去源码看 checkNotNull 校验的是哪个字段，别瞎猜。
3. **Doris 写入三大坑**：① FE 重定向用 benodes 绕开；② 依赖 checkpoint 触发 flush；③ `__DORIS_DELETE_SIGN__` 用 setDeletable(false) 关闭。
4. **SLF4J 没日志实现会吞掉所有报错**，排查问题前先确保日志能打出来。
5. **DataStream 数仓建模的核心是状态管理**：维表关联用 BroadcastState，这和 SQL 的 join 是两套思路。
6. **本地 IDEA 测试 vs 集群运行是两套环境**：本地要勾 provided scope、配 hosts、放行端口；集群内网互通反而更简单。

7. **数仓事件检测要看「流转记录」不看「当前状态」**：审批通过、拒绝、取消、签约、起租这些事件，要检测流转记录（credit_facility_status 表、各时间字段），不能看主表的 status 当前值——当前值只反映「现在停在哪个环节」，会漏掉已经流转到下一环节的数据（比如 status=16 会流转到 19）。

8. **Flink 侧输出流的类型陷阱**：异构 POJO 侧输出会触发类型传播 bug（所有 side output 被当成主输出类型，ClassCastException）。命名类、disableChaining 都救不了，统一 String(JSON) 是稳妥做法。

9. **「谁先到谁等」要分清「必须等」vs「可空」**：审批通过的 audit_man_id 必须等（每个通过都有信审经办），但拒绝/取消的 audit_man_id 可空（风控就拒的没有信审经办）。用「必须等」的逻辑去等「可空」的字段，会把该空的行永久卡住丢弃，导致漏数。

10. **credit/contract 这类有生命周期的表，按时间字段判断阶段，别按 status**：status 是「当前阶段」，时间字段（occupy_time / produce_time / signed_time）才代表「是否经历过该阶段」，两者在快照场景下结果完全不同。

11. **Flink 实时窗口聚合 + Doris 物化视图的分工**：DWS 层用 Flink 读 Kafka 做秒级实时窗口聚合（事件时间 + 水位线）；ADS 层是「历史累计」，用 Doris 异步物化视图（BUILD IMMEDIATE + 每 5 分钟自动刷新）直接从 DWD 聚合，自动维护、FineBI 直查。实时需求和累计需求用不同技术，各有优势。

12. **维度广播替代 HBase 异步 I/O**：维度表数据量小，用 Flink 从 ODS topic 广播（BroadcastState），在 BroadcastProcessFunction 里向上查 superior_*_id 拍平，比异步 I/O 简单，且和 dim 表数据一致（同一份 ODS 源）。

13. **ADS 可视化选型**：Doris 兼容 MySQL 协议，可无缝对接 FineBI / Superset / DataEase / Tableau / Power BI。大厂主流是「FineBI（商业）+ 自研 ECharts 大屏」；DataEase 是基于 Doris 的开源 BI。FineBI 直连 Doris `ads` 库的物化视图即可。
