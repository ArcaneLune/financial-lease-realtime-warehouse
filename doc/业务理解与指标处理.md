> 本文档记录本项目「按业务总线矩阵 + 实时指标体系 + 数仓分层架构，一步步实现数仓开发」的完整过程，保留每一步的业务思考（为什么这样设计、踩了什么坑、怎么取舍）。
>
> 配套：《02-数仓建模开发.md》（步骤/命令/踩坑）；本文档专注业务理解、指标体系与设计决策。

## 一、实际工作中数仓开发的流程（上游文件顺序）

真实企业里，数仓开发遵循「先有设计图、再施工」的流程，每步有对应的上游文件：

| 顺序 | 环节 | 上游文件/产出 | 决定什么 |
|---|---|---|---|
| 1 | 需求分析 | 业务需求文档 | 要解决什么问题、看什么指标 |
| 2 | 数据域划分 | 数据域清单 | 按业务主题切域（审批/授信/租赁） |
| 3 | 维度建模规划 | **业务总线矩阵** | 所有业务过程 + 维度 + 度量 → 决定建哪些事实表/维度表、每张表带哪些维度 |
| 4 | 指标定义 | **实时指标体系文档** | 原子/派生/衍生指标 + 统计周期/粒度/口径 → 决定建哪些汇总表/ADS 表 |
| 5 | 建模规范 | 分层/命名/SCD 规范 | 约束表结构、字段命名、粒度 |
| 6 | 架构设计 | 架构图 + 技术选型 | Flink/Kafka/Doris 选型、数据流向、实时性要求 |
| 7 | 开发实现 | 建表 SQL + 作业代码 | ODS→DIM→DWD→DWS→ADS 逐层落地 |
| 8 | 数据验证 | 验证脚本 | 各层数据一致性校验 |

业务总线矩阵和指标体系相当于数仓的「施工图」：数据开发先读它们，才知道建哪些表、表带哪些字段、指标怎么算、按什么粒度聚合。

## 二、业务总线矩阵分析（本项目）

### 2.1 矩阵内容（上级下发）

矩阵横向是业务过程，纵向是公共维度，交叉点 √ 表示该业务过程需要这个维度，度量是「项目个数 / 项目金额」。

| 数据域 | 业务过程（共 22 个） | 关键维度 | 度量 |
|---|---|---|---|
| 审批域 | 新增授信申请、风控审核通过/未达到风控、信审经办审核通过/拒绝、提交业务反馈、一级评审通过/拒绝、二级评审通过/拒绝、项目评审会通过/拒绝、总经理/分管总通过/拒绝、出具批复通过/拒绝、客户取消申请 | 客户、部门、风控员、业务经办、信审经办、一级/二级评审人、评审会、总经理、批复团队、业务方向、行业 | 项目个数、项目金额 |
| 授信域 | 新增授信、完成授信占用 | 客户、部门、业务经办、业务方向、行业 | 项目个数、项目金额 |
| 租赁域 | 完成合同制作、签约、起租 | 客户、部门、业务经办、业务方向、行业 | 项目个数、项目金额 |

### 2.2 业务逻辑思考（矩阵 → 事实表的取舍）

**思考 1：矩阵列了 22 个业务过程，但项目只建了 8 张事实表，为什么？**

矩阵是「全量业务过程」的规划蓝图，但实际数仓会根据**业务分析需求**合并同类过程。我的取舍：

- **审批域 17 个过程**：真正关心的是终态结果：审批通过（status=16）、拒绝（20）、取消（21）。中间的审核节点（风控、信审、一级/二级评审等）属于过程状态，不是最终事实，所以合并为 3 张事实表 `dwd_audit_approve / reject / cancel`。
- **授信域 2 个过程**：新增授信、授信占用 → `dwd_credit_add / occupy`。
- **租赁域 3 个过程**：合同制作、签约、起租 → `dwd_lease_contract_produce / sign / execution`。

**思考 2：为什么「审批通过/拒绝/取消」不能只建一张表？**

三个事件是**互斥终态**（一条申请最终只能通过/拒绝/取消），且字段不同（通过有 reply_amount、irr、period；拒绝/取消没有）。分开建模语义清晰、便于各自分析（比如「通过率」「拒绝原因」）。

**思考 3：度量「项目个数/项目金额」怎么落地？**

矩阵的度量映射到事实表的指标字段：`apply_amount`（申请金额）、`reply_amount`（批复金额，仅通过有）、`credit_amount`（授信金额，授信/租赁域有）。项目个数用 `count(*)`。

### 2.3 从矩阵推导 DWD 事实表结构

矩阵的「维度 √」决定了事实表带哪些维度字段：

| 事实表 | 维度字段（来自矩阵 √） |
|---|---|
| dwd_audit_approve/reject/cancel | 业务方向、行业、业务经办、信审经办（审批通过才有信审经办） |
| dwd_credit_add/occupy | 业务方向、行业、业务经办 |
| dwd_lease_contract_produce/sign/execution | 业务方向、行业、业务经办 |

> 业务思考：矩阵里审批域有「客户、风控员、一级/二级评审人」等维度，但事实表只保留了分析常用的维度（业务方向/行业/经办/信审经办），客户等维度留在 ODS 原始数据里，需要时用 id 关联。这是按需建模：不把矩阵所有维度都物化进事实表，避免表过宽。

## 三、实时指标体系分析（本项目）

### 3.1 指标体系内容（上级下发）

指标体系用「派生指标 = 原子指标 + 统计周期 + 统计粒度 + 业务限定」的框架定义：

- **已审项目主题**：历史至今 审批通过/取消/拒绝 项目数 + 申请/批复金额，按 6 种粒度（综合、业务方向、部门、业务经办、信审经办、行业）。
- **已审项目转化主题**：历史至今 授信漏斗 5 环节（新增授信/授信占用/合同制作/签约/起租）项目数 + 申请/批复/授信金额，综合粒度。

例如：
```
「历史至今审批通过项目数」= 原子「审批通过」count()
  + 统计周期「历史至今」+ 统计粒度「行业-业务方向-业务经办」+ 业务限定「审批通过」
「历史至今新增授信项目授信金额」= 原子「新增授信」sum(credit_amount) + 周期「历史至今」+ 粒度「窗口」
```

### 3.2 业务逻辑思考（指标 → DWS/ADS 的取舍）

**思考 1：为什么 DWS 用「窗口」粒度、ADS 用「历史至今」？**

指标系统里，上游 DWS 是「各窗口」粒度（10 秒窗口），下游 ADS 是「历史至今」累计，两级指标分层：

- DWS：细粒度（窗口），供实时监控（最近 10 秒/分钟的变化）。
- ADS：累计粒度（历史至今），供报表/大屏看总量。

「历史至今累计」= 从 DWS 窗口数据再聚合，或直接从 DWD 明细累计。本项目 ADS 用 **Doris 物化视图直接从 DWD 累计**（5 分钟刷新），避免重复计算窗口。

**思考 2：派生指标的「维度」怎么落到表？**

指标粒度「行业-业务方向-业务经办」→ DWS 表按这 3 个维度分组聚合；「信审经办」粒度 → 单独的信审经办表。这对应 DWS 的「行业经办人 3 张 + 信审经办 3 张」结构。

**思考 3：为什么转化主题只做综合粒度？**

指标系统里转化主题没有维度（统计粒度为空），因为授信漏斗是「全链路转化」，看整体转化率即可，不需要按维度拆。

### 3.3 从指标推导 DWS/ADS 表

| 指标粒度 | DWS/ADS 表 |
|---|---|
| 窗口 + 行业-业务方向-业务经办 + 审批通过/取消/拒绝 | DWS 行业经办人 3 张 |
| 窗口 + 信审经办 + 审批 | DWS 信审经办 3 张 |
| 窗口 + 无维度 + 新增授信/占用 | DWS 授信域 2 张 |
| 窗口 + 无维度 + 合同制作/签约/起租 | DWS 租赁域 3 张 |
| 历史至今 + 审批/转化 | ADS 7 张物化视图 |

## 四、分层开发过程（ODS → DIM → DWD → DWS → ADS）

### 4.1 ODS 层：Flink CDC 整库同步

**做什么**：Flink CDC 单作业读 financial_lease 全部 9 张表，debezium-json 写入 Kafka（`ods_表名`）。

**业务思考**：ODS 只做「原样采集」，保留 before/after/op 完整变更语义，因为下游要还原事件（比如审批通过是 status 从某值变为 16 的 update），必须保留变更前状态。实时数仓的 ODS 不能只存最新值。

**关键决策**：Flink CDC 2.4.2（配 Flink 1.17）；tableList 必填（正则）；动态路由按 `source.table`。

### 4.2 DIM 层：维度表

**做什么**：4 张维度表（部门/员工/行业/商业合伙人），raw mirror，Unique Key。

**业务思考**：维度表用「原始镜像」而非「拍平」，因为拍平（行业 3 级、部门 3 级）放到 DWS 用广播做，维度表保持原始结构，灵活复用（DWD/DWS 都能用）。

### 4.3 DWD 层：事实表（最核心，业务思考最多）

**做什么**：读 5 张事实源表 → 单作业动态分流 → 8 张事实表，双写 Doris + Kafka。

**业务逻辑思考（重点）**：

1. **事件识别看「流转记录」不看「当前状态」**：
   - 审批通过 = `credit_facility_status.status=16`（流水表），不是 `credit_facility.status=16`（当前值）。
   - 为什么：16 不是终态，会流转到 19（新增授信），当前停在 16 的只有少数（123 vs 1450）。这就是「快照 vs 流转」的区别：有生命周期的表，要用变更记录还原历史事件。
2. **授信/合同按时间字段判断阶段**：
   - 新增授信 = credit 插入；授信占用 = `credit_occupy_time` 非空；合同制作 = `contract_produce_time` 非空；签约 = `signed_time` 非空；起租 = `execution_time` 非空。
   - 为什么不用 status：status 是「当前阶段」，时间字段才代表「是否经历过该阶段」（一条已起租的合同必然经历过签约，但 status 已是 3）。
3. **谁先到谁等（多表关联时序）**：
   - 快照按表名字母序读，credit_facility 先于 credit_facility_status，导致关联字段（信审经办）先空后到。
   - 方法：KeyedProcessFunction + ValueState + 1h TTL，先到的存状态、后到的补全后发射。
   - 关键思考：必须等 vs 可空要分清。审批通过的 audit_man_id 必须等（每个通过都有信审经办）；拒绝/取消的 audit_man_id 可空（风控就拒、没有信审经办），用「必须等」的逻辑等「可空」字段会漏数。
4. **信审经办取 status∈(4,5,6)**：4=已分配、5=通过、6=复议，才是信审经办；status=20 是拒绝操作人，不是信审经办。
5. **Flink 异构 POJO 侧输出 bug**：统一 String(JSON)，业务状态用 POJO ValueState 内部维护。

### 4.4 DWS 层：窗口聚合 + 维度拍平

**做什么**：11 张窗口聚合表（10 秒滚动窗口），无维度 5 张 + 带维度 6 张。

**业务思考**：
- 用事件时间（各事件时间字段）+ 10 秒滚动窗口，满足「实时监控」。
- 带维度表做「行业/部门 3 级拍平 + 员工/信审经办姓名」，用广播 ODS 维度表（BroadcastState）替代参考项目里的 HBase 异步 I/O：维度表小、变化慢，广播最简单，而且和 dim 表数据一致（同一份 ODS 源）。
- 指标 REPLACE：Flink 窗口内聚好后，Doris REPLACE 幂等覆盖（同一窗口重发不累加）。

### 4.5 ADS 层：物化视图（历史累计）

**做什么**：7 张 Doris 异步物化视图（已审项目 6 粒度 + 转化主题），从 DWD + DIM 聚合，`BUILD IMMEDIATE` + `REFRESH AUTO ON SCHEDULE EVERY 5 MINUTE`。

**业务思考**：
- 「历史至今」累计用物化视图最合适：自动维护、FineBI 直查，DWD 更新后 5 分钟内 ADS 自动刷新。
- 相比 Flink 实时聚合：历史累计低频变化，日/分钟级足够，且避免重复计算窗口。
- 指标口径：各粒度 project_count/金额 = DWD 行数（验证过完全一致）。

## 五、数据验证（各层一致性）

| 层 | 验证方法 |
|---|---|
| ODS | Kafka 消息数 = 源表行数 |
| DWD | 行数/金额自洽（漏斗递减：1272→1035→940→884→702） |
| DWS | 抽样核对：DWS 窗口值 = DWD 明细窗口内聚合 |
| ADS | 各粒度 project_count/金额总和 = DWD 行数（6 粒度 × 3 结果全等） |
